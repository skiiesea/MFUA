# Vesper — учебный разбор проекта на русском

> Этот документ написан по исходникам репозитория `skiiesea/MFUA`, папка `vesper/`, ветка `main`. Его цель — помочь понять не только «что нажимает кнопка», но и как данные проходят через браузер, сервер, Socket.IO и PostgreSQL.

## 1. Сначала главное: из чего состоит Vesper

Vesper — веб-мессенджер. Он состоит из трёх основных частей:

1. **Frontend (клиент)** — React + TypeScript + Vite. Это страница, которую видит пользователь: окна, кнопки, список чатов, сообщения, профиль и настройки.
2. **Backend (сервер)** — Node.js + Express + TypeScript. Принимает запросы, проверяет права, выполняет бизнес-логику и обращается к базе.
3. **Database (база данных)** — PostgreSQL. Хранит аккаунты, чаты, сообщения, друзей, сессии и другие постоянные данные. Prisma — слой, через который TypeScript-код общается с PostgreSQL.

Дополнительно есть **Socket.IO** — канал постоянного соединения для событий в реальном времени. Благодаря ему новое сообщение может появиться у собеседника без обновления страницы.

Упрощённая схема:

```text
Пользователь
    |
    v
React-интерфейс (web/src)
    |                         \
    | HTTP /api                \ Socket.IO
    v                           v
Express (server/src/app.ts)   realtime/socket.ts
    |                           |
    +-------------+-------------+
                  |
                  v
          Сервисы и модули
                  |
                  v
          Prisma Client
                  |
                  v
             PostgreSQL
```

Важно: браузер не должен напрямую подключаться к PostgreSQL. Он общается только с сервером. Сервер — единственное место, где проверяются права доступа и выполняются защищённые операции.

## 3. Как запускается приложение

### 3.1 Корневой package.json

Файл `package.json` в папке `vesper/` — главный управляющий файл npm-проекта.

Важные понятия:

- `workspaces` объединяет папки `server` и `web` в один npm-проект.
- `npm run dev` запускает сервер и frontend параллельно через `concurrently`.
- `npm run build` сначала собирает web, затем server.
- `npm run typecheck` проверяет TypeScript в обеих частях.
- `db:*` — команды Prisma для создания клиента, проверки схемы и миграций.

### 3.2 Frontend: web/src/main.tsx

Это точка входа браузерного приложения.

- Импорты шрифтов и `index.css` подключают глобальные стили.
- `createRoot(...)` создаёт React-корень внутри HTML-элемента с id `root`.
- `StrictMode` включает дополнительные проверки React в разработке.
- `MotionConfig` задаёт общую настройку анимаций и учитывает системную настройку уменьшения движения.
- `BrowserRouter` включает маршрутизацию.
- `App` — главный компонент приложения.
- `applyUi(useUi.getState().ui)` применяет сохранённые настройки интерфейса при старте.

Знак `!` в `document.getElementById('root')!` — утверждение TypeScript: разработчик сообщает компилятору, что элемент существует. Это не создаёт элемент и не проверяет его в runtime.

### 3.3 Frontend: web/src/App.tsx

Здесь собираются страницы и правила доступа.

- `Routes` и `Route` описывают адреса страниц.
- `RequireAuth` не пускает гостя в закрытую часть приложения.
- `GuestOnly` не даёт авторизованному пользователю возвращаться на страницы входа и регистрации.
- `Outlet` показывает вложенную страницу внутри общего layout.
- При запуске `useAuth.getState().init()` проверяет, есть ли действующая сессия.
- При выходе вызывается остановка realtime-соединения, чтобы события старого пользователя не попадали в интерфейс следующего.

### 3.4 Backend: server/src/index.ts

Это точка входа сервера. Функция `main()` выполняет запуск по порядку:

1. `initStorage()` подготавливает каталоги хранения файлов.
2. `prisma.$connect()` подключается к PostgreSQL.
3. `http.createServer(createApp())` создаёт HTTP-сервер на базе Express-приложения.
4. `initSocket(server)` подключает Socket.IO к тому же HTTP-серверу.
5. `startJobs()` запускает фоновые задачи.
6. `server.listen(...)` начинает принимать подключения.

Обработчик `shutdown` нужен для корректной остановки: прекращает фоновые задачи, закрывает Socket.IO и HTTP, отключает Prisma. Обработчики `unhandledRejection` и `uncaughtException` записывают критические ошибки в логи.

### 3.5 Backend: server/src/app.ts

Здесь собирается Express-приложение:

- `helmet` добавляет HTTP-заголовки безопасности.
- `accessLogger` записывает обращения.
- `cors` задаёт разрешённые источники frontend.
- `cookieParser` разбирает cookie.
- `express.json` читает JSON-тела запросов с ограничением размера.
- `/media` отдаёт публичные изображения.
- `/api/health` — простой маршрут проверки доступности.
- `csrfGuard` и `globalLimiter` применяются перед API-маршрутами.
- Далее подключаются отдельные роутеры: auth, account, users, friends, chats и другие.
- В production сервер может отдавать собранный frontend из `web/dist`.

Порядок middleware важен: Express проходит их сверху вниз. Если middleware завершил запрос ответом, следующие обработчики уже не выполняются.

## 4. Как работает обычный HTTP-запрос

Допустим, пользователь открывает список чатов.

1. Компонент frontend вызывает функцию из Zustand store.
2. Store вызывает `api.get('/chats')`.
3. `web/src/lib/api.ts` добавляет префикс `/api`, отправляет fetch-запрос и обрабатывает ответ.
4. Express находит подключённый `chatsRouter`.
5. Middleware проверяет сессию и права пользователя.
6. Обработчик маршрута вызывает функцию сервиса.
7. Сервис запрашивает данные через Prisma.
8. PostgreSQL возвращает строки таблиц.
9. Сервер формирует DTO — объект, предназначенный для передачи клиенту.
10. Frontend получает JSON и обновляет Zustand.
11. React видит изменение состояния и перерисовывает нужные компоненты.

**Route (маршрут)** отвечает за HTTP-вход: URL, метод, проверку запроса и ответ. **Service (сервис)** содержит основную бизнес-логику. Такое разделение не даёт превращать один файл маршрутов в огромную смесь всего подряд.

### Пример из frontend: web/src/lib/api.ts

- `ApiError` — специальный класс ошибки API. Помимо текста он хранит HTTP-статус и код ошибки.
- `onUnauthorized` — callback, который можно зарегистрировать, чтобы сбросить состояние авторизации при ответе 401.
- `request<T>` — общая функция для GET/POST/PATCH/DELETE.
- `headers` — HTTP-заголовки.
- `FormData` отправляется без ручной установки Content-Type: браузер сам добавляет boundary.
- Обычные объекты превращаются в JSON через `JSON.stringify`.
- `credentials: 'same-origin'` позволяет браузеру отправлять cookie на тот же origin.
- `res.ok` означает, что HTTP-статус успешный.
- `api.get/post/patch/del` — короткие обёртки, чтобы страницам не повторять низкоуровневый fetch.

Обобщённый тип `<T>` говорит TypeScript, какой формат ответа ожидает вызывающий код. Сам по себе он не проверяет JSON в runtime — для проверки данных на границе используется Zod на сервере.

## 5. Как устроены чаты и сообщения

### 5.1 Данные в базе

В `server/prisma/schema.prisma` описаны основные сущности:

- `User` — пользователь и его профиль, настройки приватности, данные безопасности.
- `Session` — серверная сессия пользователя.
- `LoginEvent` — история попыток входа.
- `BackupCode` и `EmailToken` — резервные коды и токены почтовых операций.
- `Friendship` — заявка или подтверждённая дружба.
- `Block` — блокировка между пользователями.
- `Report` — жалоба.
- `Chat` — личный или групповой чат.
- `ChatMember` — связь пользователя с чатом, роль и отметки прочтения/доставки.
- `Message` — сообщение, автор, текст, ответ, время редактирования/удаления/закрепления.
- `Reaction` — реакция пользователя на сообщение.
- `Attachment` — файл, связанный с сообщением.
- `Notification` — уведомление пользователя.

Связи Prisma описывают отношения между таблицами. Например, `Message.chat` связывает сообщение с чатом, а `Message.sender` — с автором. `onDelete: Cascade` означает, что при удалении родительской записи связанные записи также удаляются. `@@index` создаёт индекс для ускорения частых запросов. `@@unique` запрещает дубликаты по указанным полям.

### 5.2 Отправка сообщения

В Vesper есть два связанных механизма:

- HTTP используется для загрузки истории, поиска и других запросов.
- Socket.IO используется для отправки событий и доставки обновлений в реальном времени.

Упрощённый путь отправки:

1. Пользователь нажимает кнопку отправки в компоненте Composer.
2. Клиент может сразу показать временное сообщение с временным id — это оптимистичный интерфейс.
3. Клиент отправляет событие `message:send` через Socket.IO.
4. Сервер проверяет структуру события через Zod.
5. Сервер убеждается, что отправитель состоит в чате.
6. Проверяются ограничения личной переписки, текст и вложения.
7. Сервис сохраняет сообщение в PostgreSQL.
8. Сервер отправляет `message:new` всем участникам чата.
9. Клиент получает событие и обновляет store.
10. Временное сообщение заменяется настоящим сообщением с id из базы.

**Оптимистичное обновление** — UI показывает ожидаемый результат до ответа сервера. Это делает интерфейс быстрее, но требует уметь убрать временное сообщение или отметить его ошибочным при неудаче.

### 5.3 Zustand store: web/src/store/chat.ts

Это центральное клиентское хранилище чатов.

- `create<ChatState>()` создаёт store и задаёт тип его состояния.
- `chats` — список чатов.
- `messages` — словарь сообщений по id чата.
- `hasMore` — есть ли ещё старая история.
- `detached` — загружен ли фрагмент истории вокруг конкретного сообщения.
- `typing` — кто сейчас печатает.
- `activeChatId` — открытый чат.
- `loadChats` и `loadMessages` получают данные через API.
- `addPending`, `resolvePending`, `setPendingState`, `dropPending` управляют временными сообщениями.
- `onNew`, `onUpdated`, `onDeleted` и остальные `on...` — обработчики событий реального времени.
- `set((state) => ...)` обновляет состояние. Важно возвращать новые объекты и массивы, а не менять старые напрямую: React/Zustand должны увидеть изменение ссылки.
- `get()` читает актуальное состояние store внутри действия.
- `selectUnreadTotal` — selector, вычисляющий суммарное число непрочитанных сообщений.
- `chatTitle` — небольшая функция, выбирающая заголовок личного или группового чата.

### 5.4 Socket.IO на клиенте и сервере

Клиентская часть:
- `web/src/lib/socket.ts` создаёт и закрывает socket-соединение, отправляет события.
- `web/src/lib/realtime.ts` подписывается на события и связывает их с Zustand stores.

Серверная часть:
- `server/src/realtime/hub.ts` хранит доступ к экземпляру Socket.IO и содержит вспомогательные функции отправки.
- `server/src/realtime/presence.ts` отслеживает активные соединения и присутствие пользователей.
- `server/src/realtime/socket.ts` проверяет сессию при подключении, принимает события, вызывает сервисы и рассылает результаты.

Socket.IO room — именованная группа соединений. В проекте используются комнаты пользователя и сессии, чтобы отправлять событие конкретному пользователю на все его устройства или конкретной сессии.

Событие — это имя и данные. Например, `message:new` сообщает клиенту, что появилось новое сообщение. Событие не заменяет базу данных: постоянное сообщение сначала должно быть сохранено на сервере.

## 6. Авторизация и безопасность

### 6.1 Регистрация и вход

Основная логика находится в `server/src/modules/auth/`.

- `auth.routes.ts` — HTTP-маршруты регистрации, входа и операций авторизации.
- `password.ts` — правила пароля, Argon2id-хеширование и проверка пароля.
- `session.service.ts` — создание, проверка и отзыв сессий, cookie.
- `emailTokens.ts` — токены подтверждения адреса и смены email.
- `totp.service.ts` — двухфакторная проверка TOTP.

Пароль не должен храниться в базе в открытом виде. Vesper сохраняет `passwordHash`. При входе введённый пароль проверяется против хеша.

Сессионная cookie содержит случайный токен. В базе хранится его хеш (`tokenHash`), а не исходный токен. При запросе сервер извлекает cookie, хеширует токен и ищет подходящую действующую сессию.

### 6.2 Защитные механизмы

- `middleware/auth.ts` — проверяет, что запрос принадлежит вошедшему пользователю.
- `middleware/csrf.ts` — защищает изменяющие состояние запросы от CSRF.
- `middleware/rateLimit.ts` — ограничивает частоту запросов.
- `middleware/error.ts` — приводит ошибки к единому формату ответа.
- `middleware/accessLog.ts` — журналирует HTTP-доступ.
- Zod проверяет форму входящих данных.
- Helmet задаёт защитные HTTP-заголовки.
- Проверка Origin используется для Socket.IO.
- Роли и членство проверяются на сервере, а не только скрытием кнопок в интерфейсе.

Не считай проект автоматически безопасным только потому, что в нём есть эти механизмы. Перед публикацией нужно отдельно проверить настройки HTTPS, секреты, права файлов, резервные копии, ограничения загрузки, обновления зависимостей и реальные сценарии атак.

## 7. Как читать TypeScript и React

Ниже — конструкции, которые чаще всего встречаются в исходниках.

### Импорты и экспорты

```ts
import { api } from '../lib/api';
export function loadSomething() {}
export default function App() {}
```

`import` подключает код из другого файла. `export` делает функцию, класс или значение доступным другим файлам. `export default` задаёт основной экспорт файла.

### Типы и интерфейсы

```ts
interface UserCard {
  id: string;
  displayName: string;
}
```

Интерфейс описывает форму объекта. `id: string` — поле id должно быть строкой. `?` после имени означает необязательное поле. `A | B` — значение может быть одним из нескольких типов.

### Асинхронность

```ts
const user = await prisma.user.findUnique(...);
```

`async` позволяет функции использовать `await`. `await` ждёт завершения Promise. Это не останавливает весь сервер: Node.js может обслуживать другие запросы, пока операция ожидает ввода-вывода.

### Обработка ошибок

```ts
try {
  await doWork();
} catch (error) {
  // обработка ошибки
}
```

Код внутри `try` выполняется обычным путём. Если возникает исключение, управление переходит в `catch`. Ошибку нельзя просто скрывать: пользователь должен получить понятное сообщение, а важная техническая причина должна попасть в лог.

### Массивы и объекты

- `map` преобразует каждый элемент массива в новый.
- `filter` оставляет элементы, прошедшие условие.
- `find` возвращает первый подходящий элемент.
- `some` проверяет, есть ли подходящий элемент.
- `Promise.all([...])` запускает несколько независимых асинхронных операций параллельно.
- `{ ...old, changed: value }` создаёт новый объект, копируя старые поля и заменяя одно из них.
- `?.` — optional chaining: безопасно обращается к полю, если значение не null/undefined.
- `??` — nullish coalescing: подставляет запасное значение только при null/undefined.
- `!value` — логическое НЕ; `value!` в TypeScript может быть утверждением, что значение не null.
- `=>` — стрелочная функция.
- `as Type` — утверждение типа для компилятора, а не преобразование значения в runtime.

### React-компонент

```tsx
function Greeting({ name }: { name: string }) {
  return <p>Привет, {name}!</p>;
}
```

Компонент — функция, возвращающая JSX. `name` — prop, то есть входные данные компонента. Когда props или используемое состояние меняются, React повторно вызывает компонент и обновляет DOM.

- `useState` хранит локальное состояние компонента.
- `useEffect` выполняет побочные действия после рендера: подписки, загрузки, синхронизацию.
- `useMemo` кэширует вычисленное значение, когда это оправдано.
- `useCallback` кэширует функцию.
- Zustand нужен для состояния, которое используется многими компонентами.

### Express-маршрут

```ts
router.get('/example', requireAuth, asyncHandler(async (req, res) => {
  res.json({ ok: true });
}));
```

`GET` — метод HTTP. `/example` — часть URL внутри подключённого router. `requireAuth` — middleware перед обработчиком. `req` содержит запрос, `res` формирует ответ. В Vesper обёртка `ah` помогает передавать ошибки асинхронных обработчиков в общий error middleware.

## 9. В каком порядке изучать проект

Не пытайся читать все файлы подряд. Лучше проследить одну функцию целиком.

### Маршрут №1: понять вход в аккаунт
1. `web/src/pages/Login.tsx` — форма входа.
2. `web/src/lib/api.ts` — отправка запроса.
3. `server/src/app.ts` — подключение auth router.
4. `server/src/modules/auth/auth.routes.ts` — серверный обработчик.
5. `server/src/modules/auth/password.ts` — проверка пароля.
6. `server/src/modules/auth/session.service.ts` — создание сессии.
7. `web/src/store/auth.ts` — сохранение пользователя на клиенте.

### Маршрут №2: понять отправку сообщения
1. `web/src/components/chat/Composer.tsx` — ввод текста и действие отправки.
2. `web/src/lib/socket.ts` — отправка события.
3. `server/src/realtime/socket.ts` — приём события.
4. `server/src/modules/chats/chats.service.ts` — проверки и сохранение.
5. `server/prisma/schema.prisma` — модель Message.
6. `web/src/lib/realtime.ts` — получение события.
7. `web/src/store/chat.ts` — изменение состояния.
8. `web/src/components/chat/MessageBubble.tsx` — отображение сообщения.

### Маршрут №3: понять отображение чатов
1. `web/src/pages/Messages.tsx`.
2. `web/src/components/chat/ChatList.tsx` и `ChatView.tsx`.
3. `web/src/store/chat.ts`.
4. `web/src/lib/api.ts`.
5. `server/src/modules/chats/chats.routes.ts`.
6. `server/src/modules/chats/chats.service.ts`.

### Маршрут №4: понять базу данных
1. Открой `server/prisma/schema.prisma`.
2. Найди модель `User`, затем `Chat`, `ChatMember`, `Message`.
3. Посмотри, как эти модели используются в `chats.service.ts`.
4. Сравни Prisma-запрос с соответствующей таблицей в PostgreSQL.
5. Изучи SQL-файл миграции: он показывает, какие таблицы и ограничения реально создаются.

## 10. Как безопасно экспериментировать

1. Перед изменениями создай отдельную Git-ветку.
2. Меняй одну небольшую вещь за раз.
3. Запускай `npm run typecheck`.
4. Затем `npm run build`.
5. Проверяй сценарий вручную: вход, выход, отправка сообщения, обновление страницы.
6. Если ошибка появилась после последнего изменения — посмотри diff и откати только проблемную часть.
7. Не коммить `.env`, пароли, токены, ключи и реальные пользовательские данные.

Полезные команды из корня `vesper/`:

```powershell
npm run doctor
npm run typecheck
npm run build
npm run dev
```

Для локального запуска обычно нужны установленный Node.js 20+, PostgreSQL и заполненный `server/.env`. Подробные команды настройки находятся в `README.md` и `README-WINDOWS.md`.

## 11. Что этот документ не утверждает

Этот файл — карта и учебное объяснение архитектуры по исходникам. Он не означает, что каждая функция проекта прошла тестирование или аудит безопасности. Наличие файла в репозитории не доказывает, что соответствующая функция безошибочно работает на конкретном сервере.

Также здесь не приведена буквальная расшифровка каждой строки каждого файла. В Vesper десятки исходников и тысячи строк; повторять их целиком в документации было бы неудобно и быстро устаревало бы. Вместо этого документ объясняет архитектуру, ключевые участки и назначение каждого исходного файла. Для настоящего построчного обучения лучше брать один файл за раз и разбирать его сверху вниз с привязкой к текущей версии кода.

## 12. Мини-словарь

- **API** — набор адресов и правил, по которым frontend обращается к backend.
- **Backend** — серверная часть приложения.
- **Frontend** — клиентская часть, которую видит пользователь.
- **Endpoint** — конкретный маршрут API, например `GET /api/chats`.
- **Middleware** — функция Express, выполняемая до или после обработчика маршрута.
- **DTO** — безопасная и удобная форма данных, отправляемая клиенту.
- **ORM** — инструмент для работы с базой через объекты и методы вместо ручного SQL в каждом месте.
- **Миграция** — версионированное изменение структуры базы данных.
- **Сессия** — запись, подтверждающая, что пользователь вошёл в систему.
- **Cookie** — небольшой фрагмент данных, который браузер автоматически отправляет серверу.
- **Хеширование** — одностороннее преобразование данных; пароль проверяют по хешу, а не расшифровывают.
- **Шифрование** — преобразование данных, которое можно обратить при наличии ключа.
- **WebSocket** — постоянное двустороннее соединение между клиентом и сервером.
- **Presence** — информация о том, находится ли пользователь онлайн.
- **Store** — общее хранилище состояния frontend.
- **Компонент** — самостоятельная часть React-интерфейса.
- **Prop** — входное значение React-компонента.
- **State** — данные, изменение которых может обновить интерфейс.
- **Promise** — объект результата асинхронной операции.
- **Runtime** — выполнение программы, в отличие от проверки типов компилятором.

## 13. Главное правило понимания Vesper

Когда смотришь на любую функцию, задавай себе пять вопросов:

1. Кто её вызывает — пользовательский компонент, другой сервис или Socket.IO?
2. Какие данные она получает и кто проверяет их корректность?
3. Где проверяются права пользователя?
4. Что меняется — состояние React, запись PostgreSQL или оба сразу?
5. Как результат возвращается пользователю — HTTP-ответом, realtime-событием или обоими способами?

Если можешь ответить на эти пять вопросов для функции, ты уже понимаешь её место в архитектуре Vesper.
